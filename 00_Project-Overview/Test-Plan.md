
Test Plan

1. Introduction

1.1 Purpose

The purpose of this Test Plan is to define the testing approach, objectives, scope, resources, and activities for this educational QA project.

The document describes how testing activities will be organized and performed during practical exercises.

1.2 Project Description

This project is an educational QA portfolio focused on developing practical software testing skills.

Testing activities include web application testing, API testing, test design techniques, SQL practice, and basic test automation.

1.3 Test Objectives

The main objectives are:

- Practice different types and levels of software testing.
- Create test cases, checklists, and bug reports.
- Identify and document defects.
- Gain practical experience with testing tools.
- Develop analytical and technical skills.
2. Test Scope

2.1 In Scope

The following activities are included in this educational project:

- Functional testing of web applications.
- UI testing and checking user interface elements.
- Positive and negative testing.
- Exploratory testing.
- Regression testing of previously checked functionality.
- API testing using Postman.
- Test design techniques, including equivalence partitioning and boundary value analysis.
- Basic SQL queries and database validation exercises.
- Basic UI test automation using JavaScript and Playwright.
- Creating and maintaining test documentation.

 2.2 Out of Scope

The following activities are not included in the current project scope:

- Testing production systems without permission.
- Testing real payment transactions.
- Load and stress testing.
- Penetration testing and advanced security testing.
- Testing internal application code without access to the source code.
- Testing functionality that is unavailable in the selected practice environments.

3. Test Strategy

3.1 Testing Approach

A combination of manual and automated testing approaches will be used.

Manual testing will be the primary approach during the initial stages of the project. Automation will be introduced gradually as practical skills in JavaScript and Playwright develop.

3.2 Types of Testing

The following testing types and techniques will be practiced:

- **Functional Testing** — verifying that application functionality works according to expected behavior.
- **UI Testing** — checking interface elements, layout, and user interactions.
- **Smoke Testing** — checking the basic functionality of an application.
- **Regression Testing** — verifying that existing functionality has not been affected by changes.
- **Exploratory Testing** — exploring an application to identify unexpected behavior.
- **Positive Testing** — checking the application with valid input data.
- **Negative Testing** — checking how the application handles invalid input data.
- **API Testing** — checking API requests, responses, status codes, and data.
- **Basic Automated Testing** — writing and executing automated UI tests.

 3.3 Test Design Techniques

The following test design techniques will be applied:

- Equivalence Partitioning.
- Boundary Value Analysis.
- Decision Table Testing.
- State Transition Testing.
- Checklist-based testing.
- Use Case Testing.

3.4 Defect Management

Identified defects will be documented in bug reports.

Each bug report should contain:

- Bug ID.
- Summary.
- Environment.
- Preconditions.
- Steps to Reproduce.
- Actual Result.
- Expected Result.
- Severity.
- Priority.
- Attachments, if applicable.

4. Test Environment

4.1 Hardware and Software

The testing environment may include:

- Personal computer running macOS.
- Web browsers: Google Chrome and Safari.
- Visual Studio Code.
- Terminal.
- Git and GitHub.

4.2 Testing Tools

The following tools will be used during practical exercises:

| Tool | Purpose |
|---|---|
| Chrome DevTools | Inspecting web pages and debugging UI behavior |
| Postman | Sending and validating API requests |
| SQL | Practicing database queries |
| Git | Version control |
| GitHub | Storing and managing project documentation |
| Visual Studio Code | Editing files and working with code |
| Playwright | UI test automation |
| JavaScript | Writing automated tests |

4.3 Test Environments

The project will use publicly available educational testing environments, including:

- The Internet — UI and functional testing.
- AcademyBugs — bug hunting and defect reporting.
- Restful Booker — API testing.
- ParkCalc — test design exercises.
- SQLBolt — SQL practice.

## 5. Test Data

### 5.1 Test Data Requirements

Test data will be selected according to the functionality being tested.

The following data categories may be used:

- Valid input data.
- Invalid input data.
- Empty values.
- Boundary values.
- Special characters.
- Different data formats.
- Test user information.

### 5.2 Test Data Management

Test data will be created specifically for educational exercises.

Only fictional or publicly provided test data will be used. Real personal or confidential information will not be included in the project documentation.

## 6. Entry and Exit Criteria

### 6.1 Entry Criteria

Testing activities can begin when:

- The selected application or testing environment is available.
- The functionality to be tested is identified.
- Basic requirements or expected behavior are understood.
- Test data is prepared.
- The necessary tools are available.
- Test documentation is ready, where applicable.

### 6.2 Exit Criteria

A testing activity can be considered completed when:

- Planned test cases or checklist items have been executed.
- Actual results have been documented.
- Identified defects have been recorded.
- Test results have been summarized.
- Known limitations and unresolved issues have been documented.

The completion of an educational exercise does not necessarily mean that the tested application is completely defect-free.

## 7. Risks and Limitations

### 7.1 Risks

The following risks may affect testing activities:

- Public testing environments may become unavailable.
- Application functionality may change without prior notice.
- Requirements or expected results may be incomplete.
- Some defects may be difficult to reproduce.
- Limited access to application functionality may restrict testing.
- Lack of commercial testing experience may affect the depth of analysis.

### 7.2 Limitations

This is an independent educational project.

Testing activities are performed in publicly available practice environments and do not represent commercial testing experience.

The project does not include access to private production systems, internal databases, or confidential application information.

## 8. Test Deliverables

The following artifacts are expected to be created during the project:

- Test Plans.
- Test Checklists.
- Test Cases.
- Bug Reports.
- API Testing Collections and Results.
- SQL Queries and Exercises.
- Test Execution Results.
- Screenshots and Supporting Evidence.
- Test Summary Reports.
- Basic Automated UI Tests.

All documentation and practical results will be stored in the GitHub repository.

## 9. Test Completion and Reporting

### 9.1 Test Execution

Testing activities will be performed according to the defined scope and selected testing approach.

Test cases and checklist items will be executed manually or automatically, depending on the exercise.

The results will be recorded as:

- Passed.
- Failed.
- Blocked.
- Not Run.

### 9.2 Test Reporting

After completing a testing activity, a summary report may include:

- Scope of testing.
- Testing activities performed.
- Number of executed test cases.
- Number of passed and failed tests.
- Identified defects.
- Known limitations.
- Overall testing results.

### 9.3 Project Status

This Test Plan is a working document and may be updated as the educational project develops.

New testing activities, tools, and documentation may be added as practical experience grows.
